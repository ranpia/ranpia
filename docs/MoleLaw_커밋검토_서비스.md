# MoleLaw 서비스 커밋별 검토

검토일: 2026-10-23. 개인 재구축의 서비스 변경을 검토했다. 읽기 기준은 `ranpia/MoleLaw_backend`의 아래 7개 커밋이며, 확인 시 최신 `dev`는 `7962c44`다. 로컬 읽기 경로는 `.tools/MoleLaw_review`다. `git show`로 각 시점의 diff·연결 문서·구현·테스트를 대조했다. 테스트를 재실행하거나 프로젝트 서버·DB에 접속하지 않았다. 아래 실행 결과는 저장소에 남은 당시 기록이며 이번 검토의 실행 결과가 아니다.

## 실패 관찰에서 개발 판단으로 연결되는 사례

### 1. 검색과 색인의 호출 예산을 분리

`2225a12`의 [실행 기록](https://github.com/ranpia/MoleLaw_backend/blob/2225a12/docs/validation-status.md)은 크레딧 소진, 판단 출력 제약 오류, 공유 예산 소진을 서로 다른 실패로 기록한다. 크레딧 문제 해소 후 실제 공항 질문에서 공항시설법 228청크를 KURE·Qdrant로 적재·검증하고 15조문을 재검색했지만, 다음 법령의 전체 색인 중 공유 HTTP 128회가 소진됐다. 따라서 이 실행을 첫 답변·방 저장 성공으로 기록하지 않았다.

한 상담에 발생하는 모든 HTTP 호출을 같은 한도로 제한하면 법령 분량에 비례하는 임베딩·색인 배치가 검색에 필요한 예산까지 소진한다. 변경에서는 일반 검색/수집 128회, 임베딩/색인 각각 기본 1024회로 책임을 나누되 실행 전체 누적·중도 한도 변경 금지·후속 상담 금지를 유지했다. 법령별 새 세션에서는 모델 revision을 확인하고 배치 실패 후에도 다시 확인한다. 임베딩은 일반 처리 시간에서 분리하지만 자체 누적 900초 한도는 유지한다.

근거는 [LegalToolContext](https://github.com/ranpia/MoleLaw_backend/blob/2225a12/src/main/java/com/MoleLaw_backend/law/service/tool/LegalToolContext.java)와 `LegalToolContextEmbeddingTimeTest`다. 테스트는 수백 번의 벡터 호출이 검색 한도를 차감하지 않는지, 각 한도 초과·변경·후속 사용을 거절하는지 검사한다. 기록상 128개를 넘는 합성 조문 적재·누락 복구·재검색을 검색 예산 4회로 완료했다. 이 수정 뒤 실제 공항 질문을 추가 재요청하지 않았으므로 **실제 실패 원인을 바탕으로 예산 구조를 고치고 모의 회귀를 확인한 경험**으로 쓰는 것이 정확하다.

### 2. 후보 발견과 근거 본문 읽기를 분리

기존 2500토큰 판단 입력 안에서 긴 본문을 제한하면 검색 후보 수와 실제 판단에 전달한 조문 수가 달라진다. `2225a12`는 최대 15개의 메타데이터 목록을 먼저 비교하고, 모델이 고른 최대 8개 ID만 서버가 읽도록 구성했다. 모델은 임의 원문 UUID를 읽을 수 없으며 현재 후보 ID 소속을 먼저 검사한다. Qdrant의 후보와 MySQL의 불변 원문은 법령 ID·MST·시행일·출처·제목·본문까지 대조한다. 새 법령 API나 임베딩을 호출하는 단계가 아니다.

선택 모델은 읽기 대상을 제안하고 서버는 권한·원문 동일성·입력 크기를 결정한다. 목록 4000, 본문 누적 12000, 최종 결합 입력 20000의 로컬 추정 토큰 한도를 분리했다. 초과한 조문을 잘라 전체 조문처럼 전달하지 않고 `BODY_BUDGET_EXCEEDED`로 남긴다. 실제 읽지 않은 ID는 충분성 판단에서 승인할 수 없다.

근거는 [읽기 계약](https://github.com/ranpia/MoleLaw_backend/blob/2225a12/docs/evidence-reading.md), `EvidenceReadToolService`, `EvidenceReadPlannerTest`, `EvidenceDecisionPlannerTest`다. 15개 목록 전달·긴 본문 보류 후 짧은 본문 선택·누적 한도·미등록 ID·원문/시행 버전 불일치·읽지 않은 ID 승인 거절을 검사한다. 로컬 추정치는 실제 청구 토큰이 아니고, 관련 법령 다양성이나 법률 답변 정확도가 보장된다는 뜻도 아니다.

### 3. 반복 선택을 처리할 때 이미 읽은 근거 보존

실제 로그에는 색인 검증 성공 후 `readCount=4`에서 `IllegalArgumentException`이 발생했다고 기록돼 있다. 원시 모델 응답이 없어 해당 실요청의 정확한 원인은 확정하지 않았다. 다만 코드 검토에서 다음 읽기 라운드가 같은 ID를 다시 선택하면 기존 본문까지 실패 처리하는 경로를 발견하고 회귀 테스트로 재현했다.

`EvidenceReadPlanner`는 이미 시도한 ID를 다음 목록에서 제외하고, 그래도 재선택하면 신규 ID만 읽는다. 새 ID가 없으면 기존 본문을 보존하고 종료한다. 한 응답 안의 중복·미등록 ID 거절은 유지한다. 즉 계약 위반과 허용 가능한 반복을 구분했다. `alreadyReadIdsAreSkippedWithoutLosingVerifiedEvidence`는 같은 ID를 두 번 응답하는 모델 대역에 대해 본문 읽기가 한 번이며 기존 본문이 반환되는지 검사한다. 진단도 모델 선택·선택 계약·원문 읽기로 나눴다. 당시 기록은 전체 382개, 실패 0, 건너뜀 2이며 실제 유료 LLM 재요청은 하지 않았다.

### 4. 완료 세대와 물리적 저장 상태를 함께 검사

`d6c5786`은 MySQL의 색인 세대 상태로 검색 가능한 범위를 구분했다. `437543d`는 모든 임베딩·적재가 성공한 뒤 완료 상태로 전환하는 ETL을 구성했다. `2225a12`에서는 완료 표시만 믿지 않고 포인트 ID·개수·세대·원문 해시·모델 revision·법령 버전을 실제 Qdrant와 대조하는 검증을 추가했다.

`LawQdrantDocumentWriter.accept`는 벡터를 모두 확보한 뒤 적재하고 `verify` 성공 후 반환한다. 상위 서비스는 그 뒤에 완료 상태를 기록한다. 기존 완료 색인도 재사용 시 재검증하고 누락이면 새 세대로 전체 재처리한다. 저장 포인트를 제거한 뒤 복구하는 대역/격리 Qdrant 테스트가 기록돼 있다. 이는 부분 색인을 검색에서 제외하는 경계이며 영속 작업 큐·프로세스 중단 재개·분산 중복 방지·구세대 물리 삭제를 완성한 것은 아니다.

### 5. Advisor 도입을 대화·근거·저장 책임 분리로 설명

`06ba8a8`에서는 과거 대화는 `MessageChatMemoryAdvisor`, 원문 근거는 고정 스냅샷, 성공한 턴 저장은 서버 서비스가 맡는다. 이전 assistant 답변을 법적 근거로 재사용하지 않도록 구분하고 소유권을 메모리 조회 시에도 확인한다. `8e0080e`에서는 생성 서비스와 저장 서비스를 정리하고 저장 실패 시 질문만 남는 경우를 트랜잭션 테스트로 다룬다.

이 사례의 강점은 프레임워크를 추가했다는 사실보다 **자동 메모리 콜백과 기존 저장 책임의 충돌을 피하고, 답변 근거와 대화 맥락의 역할을 구분한 설계**에 있다. Advisor가 탈옥을 차단했다고 쓰지 않는다. 현재 확인한 제약은 서버의 ID·소유권·출처·저장 계약이며, 의미 수준의 근거 충실성과 보안 공격 대응 평가는 별개다.

## 이력서에 권장하는 사례

1. **대표 문제 해결: 공유 호출 예산 소진.** 실제 상담의 실패 지점과 이후 구조 변경·회귀 검증 범위가 구체적이다. “실제 법령 색인 과정에서 공통 HTTP 한도가 소진되는 문제를 확인해 검색·임베딩·색인 예산을 분리하고, 대형 합성 조문으로 누적 상한과 검색 예산 보존을 검증했습니다.” 실제 상담 정상화까지 확인했다고 덧붙이지 않는다.
2. **RAG 설계 경험: 후보 목록과 본문 읽기 분리.** “검색 후보 전체를 비교한 뒤 서버가 허용된 ID의 동일 버전 원문만 복원하도록 나누고, 읽지 않은 근거의 승인과 인용을 거절하도록 구현했습니다.” 정확도 개선 수치 없이 구현 선택과 검사 범위를 설명할 수 있다.
3. **성장 경험: 반복 선택과 실패 보존.** “읽기 라운드의 동일 ID 재선택이 확보한 근거까지 실패시키는 경로를 재현하고, 중복 읽기는 생략하면서 기존 본문을 보존하도록 수정했습니다.” 실제 로그의 정확한 예외 원인을 확정했다는 표현은 피한다.
4. **Spring AI 경험: Advisor·스냅샷·저장 분리.** 시스템 프롬프트 중심 구현에서 역할별 Client와 서버 검증으로 확장한 변화로 설명한다. 메모리 Advisor 도입을 탈옥 차단 성과로 바꾸지 않는다.

암호화·dotenv·Swagger 사례는 구현 범위를 보여주는 보조 경험으로 두고, RAG 주 담당이라는 기존 역할과 연결되는 위 사례를 먼저 제시하는 편이 자연스럽다. 작성자의 개인적인 배움·판단 계기는 사용자 설명으로 추가 확인해야 한다.
