# MoleLaw 개인 재구축

2025년 팀장으로 참여한 법률 상담 서비스를 포크해 2026년 10월부터 개인적으로 재구축하고 있다. 기존 팀의 개발 기간·역할과 후속 개인 작업을 구분한다.

검토 기준: 2026-10-14 원격 `dev`의 `61a4823`. 같은 시점 `main`은 `ec9d87b`이며 `dev`에만 있는 커밋은 병합 포함 10개다. 문서와 구현은 이 리비전을 기준으로 읽었으며 테스트·운영 환경을 이번 검토에서 실행하지 않았다.

## 기존 구현에서 출발한 문제

초기 프로젝트는 외부 모델 호출, 법령 검색, 프롬프트 구성과 답변 반환을 빠르게 연결한 형태였다. 후속 문서에서는 기능 추가보다 책임과 실패 경계를 먼저 정리한다. 특히 인증 토큰의 용도·폐기, 수집한 원문의 재현 가능성, 검색 결과와 답변 근거의 연결을 별도 문제로 다룬다.

이력서에서는 초기 RAG 구현 경험에 이어 **기존 코드를 검토하고 실패 조건과 저장소 역할을 다시 설계한 경험**으로 설명할 수 있다.

## 구현한 변경과 선택 이유

### 모델 호출 공통화

`8ac5f37`에서 직접 작성한 모델 API 호출을 Spring AI `ChatClient`와 `EmbeddingModel` 기반으로 통합했다. 여러 서비스의 호출 방식을 공통화하고 임베딩의 차원·유한값 검증을 추가했다. Qdrant 설정 준비와 실제 검색 경로 전환은 구분한다.

### 인증의 가용성과 폐기 범위 선택

인증 설계는 단계적으로 바뀌었다. `main`의 Redis Access 등록 방식은 `dev`의 `83ca4df`에서 제거했다. 현재는 최대 5분 Access JWT를 검증하고, 사용자 존재와 현재 권한은 MySQL에서 확인한다. 따라서 stateless 토큰이라고 해서 모든 저장소 의존성이 없는 것은 아니다.

이 선택은 매 Access 인증의 Redis 의존성을 없애는 대신 로그아웃·비밀번호 변경 후 복사된 Access가 만료까지 최대 5분 유효할 수 있음을 받아들인다. 이를 ‘즉시 폐기’ 또는 ‘탈취 방지 완성’으로 표현하지 않는다.

`0d3775c`에서는 JWT Refresh를 난수 토큰으로 교체했다. Redis에 원문 대신 SHA-256 해시와 로그인 family·소비 이력·절대 만료를 기록하고 Lua로 회전·재사용 판정을 처리한다. 이미 소비한 토큰의 재사용은 해당 family를 폐기하며, 임의 secret을 제출한 요청은 정상 family를 폐기하지 않는다. 비밀번호 변경·탈퇴는 사용자 세대를 바꿔 기존 Refresh family를 거절한다.

Redis 장애 시 기존 Access 인증은 유지하되 로그인·재발급·Refresh 폐기는 503으로 실패한다. MySQL과 Redis를 하나의 트랜잭션으로 가정하지 않고, 계정 잠금·변경 순서와 부분 실패 정책을 문서화했다. 동시 재발급·응답 유실 시 재로그인이 필요할 수 있다는 제약도 명시한다.

### 법령 조회와 원문 보존

`6afaae9`에서 법령·판례 목록/상세 조회를 네 내부 Tool로 구성했다. 서버가 입력 필터·후보 ID·중복 페이지·호출 및 시간 예산을 검증하고, 원문 JSON·해시·조회 시점·출처 식별자를 보존한다.

이 기능은 이후 근거 추적과 재색인의 기반이다. 현재 공개 MCP 서버, 모델의 자동 tool-calling 또는 상담 API와의 연결까지 완료한 것은 아니다. 원문 스냅샷 저장과 상담방별 확정 근거 저장도 구분한다.

### 스키마와 검증 환경

`b92c4c5`에서 Flyway V1 초기 스키마와 JPA validate, 독립 MySQL 통합 테스트를 추가했다. 일반 테스트의 H2·모킹과 실제 저장소 통합 테스트를 나눠 외부 의존성 없이 확인할 범위와 실제 저장소에서 확인할 범위를 구분한다.

프로젝트 문서는 일반 테스트 148개·Redis 11개·MySQL 2개 통과 이력을 기록한다. 이는 저장소에 기록된 개발 당시 결과이며 이번 이력서 검토에서 재실행한 결과가 아니다. 운영 배포·브라우저 통합 검증 완료로 확장하지 않는다.

## 문서에 담긴 후속 설계

다음은 구현 성과가 아닌 설계·개발 계획이다.

- **원문과 검색 색인의 역할 분리:** MySQL 원문을 기준으로 Qdrant를 재생성 가능한 색인으로 취급한다. 법령 버전·청킹·임베딩 모델·차원을 추적하고 부분 실패를 재실행할 계획이다.
- **최초 상담과 후속 상담의 경계:** 최초 질문은 실행 예산 안에서 수집·재검색하고, 후속 질문은 확정 근거와 대화만 사용한다. 새 쟁점은 새 상담을 안내해 근거가 대화 중 조용히 바뀌지 않도록 설계한다.
- **서버와 모델의 책임 분리:** 모델은 검색 조건과 후보를 제안하고 서버는 권한·도구·예산·상태·출처를 검증한다. 초기부터 자동 도구 호출이나 멀티 에이전트를 붙이지 않고 기본 RAG 평가 후 필요성을 판단한다.
- **완료 조건의 분리:** 인프라 연결, 저장소 통합, 회귀 테스트, 검색·답변 품질 평가는 별개다. Recall@K·근거 충실성·지연·비용을 비교할 계획이며 개선 수치는 아직 성과로 제시하지 않는다.

Qdrant 검색·ETL·Ollama 애플리케이션 연동, 상담방 근거 스냅샷, Advisor 대화 메모리, 역할별 오케스트레이터와 SerpApi 도입은 완료 항목으로 쓰지 않는다. 최신 인증 정책은 이전 문서의 Redis Access·MySQL Refresh 제안을 대체한다.

## 사용자 확인: 임베딩 비교 계획 (2026-10-15)

여러 임베딩 방식을 적용·비교하는 실험은 아직 수행하지 않았다. 사용자는 앞으로 질문과 법령의 유사도를 비교해 사용할 방식을 선정할 계획이라고 설명했다. 기존 임베딩 검색 구현과 여러 방식의 비교 검증 경험은 구분한다. 후보 방식과 평가 데이터, 선정 기준은 후속 설계에서 구체화하며 검색 품질 개선 결과는 아직 없다.

## 교육에서 재구축으로 이어진 배경 (2026-10-15)

사용자 설명에 따르면 팀 개발 당시에는 Spring AI를 알지 못했다. 이후 교육에서 오케스트레이터 개념을 접했고, 임베딩 검색과 챗봇을 연결하는 흐름을 조정하면서 법령·판례 조회를 Tool로 활용하려는 목적으로 재구축을 진행하고 있다.

2026-10-15 GitHub 재확인에서도 `dev=61a4823`, `main=ec9d87b`였다. Spring AI 호출 통합과 내부 Tool은 구현돼 있으나 `docs/legal-api-tools.md`는 ChatClient에 Tool을 등록하지 않는다고 명시한다. `docs/plans/orchestration-models.md`의 검색 계획·근거 검토·답변 역할별 오케스트레이터는 계획 상태다. 학습 내용을 설계와 일부 구현에 적용한 경험으로 설명하며 전체 상담 연결 완료로 표현하지 않는다.

## Advisor 활용과 챗봇 제약 검증 계획 (2026-10-15)

사용자는 기존 GPT 챗봇에서 주로 시스템 프롬프트를 사용했고 Advisor를 활용하지 못한 아쉬움이 있다고 설명했다. 개인 재구축에서는 Spring AI Advisor로 챗봇에 제약을 적용하고 탈옥 등 보안 문제에 대응하려는 목표가 있다. 아직 구현·효과 검증이 완료된 경험은 아니다.

자기소개서 초안에는 요청·응답 검증, 서버의 도구 실행 제한, 탈옥·프롬프트 인젝션 시도와 정상 질문을 함께 평가하는 방향으로 구체화했다. 이는 작성 과정에서 제안한 후속 검증 방향이며, 확정된 구현 명세나 수행 결과로 취급하지 않는다. 기존 대화 메모리 Advisor 계획과 이번 제약·보안 검증 목표는 구분한다.
